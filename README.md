# sm64-AI-binds

AI experiments on Super Mario 64, running the decomp port from `../sm64-binds`. The main project is **objective-RRT v2** (`objective-rrt-v2/`, a Cargo workspace): a tree search that grows a tree of game states from power-on. Pluggable *objectives* (collect a star, enter a door, do a BLJ, ...) each give a per-state **ETA in frames** to their goal; a genetic algorithm (or a rolling-horizon controller) finds each segment's inputs by minimising that ETA; the tree keeps what it reaches. The goal is collecting stars as fast as possible in game time.

You need the US ROM at `baserom.us.z64` (md5 `20b854b239203baf6c961b850a4a51a2`). Never commit or publish it, or anything derived from it.

v1 (`objective-rrt/`, the progress-based RRT, scattershot and the curiosity GA) is gone from the tree; the tag `archive/pre-condense` has all of it, and `objective-rrt-v2/RUNS.md` logs the experiments.

## Layout (`objective-rrt-v2/`)

| Crate / path | What |
|---|---|
| `env/` (`obrrt-env`) | `SearchConfig`: every setting of the search as plain typed data (the docs on its fields are the switch reference), with adapters from the `OBRRT_*` environment (`from_env`) and a TOML file. Production settings are the defaults |
| `core/` (`obrrt-core`) | The contract between search and domain: the game state `St` and its objects, the memory layout (`layout.rs`, generated by `tools/gen_layout.py`), static geometry (`geo.rs`), the `Objective` trait (`eta`, `base_criteria`, `steer_target`, `pad_overlay`, ...), the `Mover` trait, and the process pieces: `config` (the config an engine's threads run under, `per_config!` caches), `runtime` (an engine's own run-time state: position goal, published zones, caches), `posgoal`, `records` |
| `search/` (`obrrt-search`) | The engine, with no SM64 knowledge beyond `steer.rs`: tree (`tree.rs`), planning and merge (`engine.rs`), the objective pool with its rate sampler (`pool.rs`), the open-loop GA (`ga.rs`) and the rolling-horizon controller (`ga/rhstep.rs`), dense adds (`dense.rs`), route chains, the move-policy genomes (`movegenome.rs`), the quality-diversity archive (`qd.rs`), the walkable-distance road (`road.rs`), diagnostics |
| `objectives/` (`obrrt-objectives`) | All SM64 knowledge: about 140 objective kinds (stars, doors, paintings, collectibles, enemies, bosses, NPCs, rides, missions) plus the speedrun techniques (`src/extra/tech/`) and the movement library (`src/moves/`) that steers and supplies the GA's policies. See `objectives/OBJECTIVES.md` |
| `run/` | `obrrt2`, the search driver, and the tools around its trees: `nodepath`, `tasplay`, `probe`, `ilsync`, `obrrt-route`, `dataset`, `funnel`; `tests/two_configs.rs` runs two engines with different configs in one process |
| `spec/` (`obrrt-spec`) | Declarative objectives interpreted from JSON, the validator (`spec-validate`), the landmark-route solver `legs`, `mend`, `route-stats`. See `tools/spec/README.md` |
| `agent/` (`ar`) | Agent-driven routes: an LLM keeps a window of objectives filled while a daemon solves them with the rolling-horizon GA. See `agent/README.md` |
| `oss2/` | Scattershot v2: the Go-Explore archive with the v2 GA as an expansion operator (`oss2/README.md`); `scattershot/` is the vendored original it builds on |
| `gp/`, `policy/` | Genetic-programming movement controllers and the reactive policy inventory (policies are never deleted: they are retired by a status flag) |
| `tools/` | Python and shell: `seg120/` (the 120-star campaign), `spec/` (the Eureka-style objective loop), `analysis/`, `king_loop.py`, `screen.sh` / `arm_eval.sh` (screens), viewer export (`viz.py`, `export_tree.py`), TAS analysis |
| `GOALS.md`, `RUNS.md`, `STAR120*.md` | How objectives are written; the run log; the 120-star plan and audit |
| `../backbone/` | PyTorch state backbone and heads trained on trees and the TAS |

## 1. Build

Run from `objective-rrt-v2/`:

```sh
cargo build --release                       # default members: env, core, search, objectives, run -> target/release/obrrt2
cargo build --release -p obrrt-spec        # legs, spec-validate, mend
cargo build --release -p obrrt-agent --bin ar
cargo test --workspace --release -- --test-threads=4     # two_configs needs SM64_ROM=<rom>, else it skips
```

A global rustc gate (`/workspaces/sm64-combined/.cargo/rustc-gate.sh`) allows a limited number of rustc at once machine-wide, so parallel builds queue instead of running out of memory.

## 2. Run the tree search

```sh
obrrt2 <rom> [out_dir=runs/obrrt] [seed=1] [minutes=30] [<start.m64>]
```

The production settings (movement library, move GA, calm jumping, Lakitu arc, fast painting entries, swim hold, ground-pound catch, soft dedup, route chains, the rate sampler, dense adds of the last generation, kinship x10, the 0.75 move weight) are the defaults. What you set is the budget and the run's shape:

```sh
env OBRRT_MEM_MB=3000 OBRRT_ROUND=64 OBRRT_MAX_FRAMES=500000000 OBRRT_TAS_BOOT=1 \
  ./target/release/obrrt2 ../baserom.us.z64 runs/my-run 1 180 > logs/my-run.log 2>&1
```

- **Reproducible:** the same binary, seed and thread count (`RAYON_NUM_THREADS`) give byte-identical trees (compare `tree.bin` and `nodes.csv` before and after a change to check a refactor).
- **Budget:** `minutes` is a wall-clock cap. `OBRRT_MAX_FRAMES` ends the run by emulated frames instead.
- **Boot from a movie:** `<start.m64>` boots from a movie prefix; `OBRRT_BOOT_NOWAIT=1` starts where the prefix ends even if Mario is moving. `OBRRT_TAS_BOOT=1` is the menus-only boot.
- **Resume:** `OBRRT_RESUME=runs/my-run` continues an existing tree.
- **Time:** all frame counts are frames since power-on (`St.frame`), at 30 per second.

Outputs in `runs/my-run/`: `nodes.csv` (one row per state), `events.jsonl` (every attempt), `summary.json`, `tree.bin` (inputs, for resume and replays), `first-*.m64` and `frontier-*.m64` (replays from power-on). The log prints progress every 30 s plus "best times" per star count and "first arrivals".

## 3. How the search works

1. **Objectives.** For a base state `b` the `Registry` generates objectives; each has `base_criteria` (which states may start it), `exists_in`, and `eta(state, start, mem)`: the frames it still needs, `Done` when met, `Lost` when hopeless. Technique objectives credit only the signature of the trick, never plain walking.
2. **Plan.** A round of attempts (`OBRRT_ROUND`, 64) is planned from the tree: a `b` from the frontier cells (soft-dedup weighted), an objective from the pool (weights adapted by a rate sampler: improvement per frame spent), a start state near `b`, and optional route chains (a follow-on objective where the best routes went on). Goal focus, new-eligible queues and the web miner's position bubble steer some plans.
3. **Attempt.** The GA (or the rolling-horizon controller, `OBRRT_RH=1`) plays rollouts under the movement library's steering and the objective's pad overlay; fitness is the best discounted sum of per-frame ETA decreases (gamma `OBRRT_GA_GAMMA`, 0.99), with a bonus on `Done` and a penalty on death. The winner's inputs become a segment; the last generation's end states are dense candidates.
4. **Merge.** Segments are merged in order against the tree: a state is kept when it is new by the dedupe cell or sooner than the one there; sparse saves keep memory bounded.
5. **Settings and state.** Every setting is a field of `SearchConfig`; an engine runs its threads under its own config and `Runtime`, so two searches with different settings run in one process and each makes the tree it makes alone (`run/tests/two_configs.rs`).

## 4. Look at results

- **Stars:** `python3 tools/stars.py <run>` (a few runs at a time); `tools/v2sum.py` for star times, `tools/compare.py` for milestones.
- **Viewer, live tree:** `python3 tools/viz.py 8090 &` (tree server), then the viewer front end in `../../sm64-viewer/frontend` (`npx vite`); `python3 tools/export_tree.py <run>` for a static export.
- **Replay tools:** `nodepath <run> <node>` (an m64 from power-on to a node), `tasplay` (play an m64 and dump per-frame state), `probe` (inspect a frame); `cargo run --release --example core_fields`.

## 5. Mupen64 savestates

`../sm64-binds` loads Mupen64-rr(-lua) and Mupen64Plus `.st` files into the port: `MupenState::from_file`, `load_mupen_state`, `warp_to_mupen_area`, and the check tool `cargo run --release --example mupen_check`. Formats and limits are in `../sm64-binds/docs/mupen64-st.md`.

## Rules the code follows

- SM64 knowledge lives only in `objectives/` (and `search/src/steer.rs`). The engine is generic. Heuristics use straight-line distance and per-state ETAs.
- No MCTS or UCB over states: RRT-style selection.
- Technique objectives must require the trick in their progress and success, never credit plain walking. Location techniques get only a rough start region and an endpoint; the general technique code does the rest.
- Rust is the single source of truth for the search; Python is tooling around it.
- One engine, one set of production defaults: an experiment that loses is deleted (tag `archive/pre-condense` and RUNS.md keep it), not left behind a switch.
