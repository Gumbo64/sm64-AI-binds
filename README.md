# sm64-AI-binds

AI experiments on Super Mario 64, running the decomp port from `../sm64-binds`. The main project is **Objective-RRT** (`objective-rrt/`): a tree search that grows a tree of game states from power-on. Pluggable *objectives* (collect a star, enter a door, do a BLJ, ...) each supply a base condition, a straight-line heuristic, a success test, graded progress and steering hints. A GA finds each segment's inputs. The goal is collecting stars, as fast as possible in game time.

You need the US ROM at `baserom.us.z64` (md5 `20b854b239203baf6c961b850a4a51a2`). Never commit or publish it, or anything derived from it.

## Layout

| Path | What |
|---|---|
| `objective-rrt/core/` | Game state (`St`), memory layout (`layout.rs`, generated by `tools/gen_layout.py`), static geometry queries (`geo.rs`), the `Objective` trait |
| `objective-rrt/search/` | The engine: tree, frontier, dedupe, start selection, GA (`ga.rs`), steering (`steer.rs`), extras (`backchain.rs`, route bench). No SM64 knowledge beyond `steer.rs` |
| `objective-rrt/objectives/` | All SM64 knowledge: about 140 objective kinds plus speedrun techniques (`src/extra/tech/`). See `objectives/OBJECTIVES.md` |
| `objective-rrt/run/` | Binaries: `obrrt` (the search), `nodepath`, `tasplay`, `probe`, `steertest`, `modalbench`, `obrrt-route`, `ilsync`; plus examples (`core_fields`, labs) |
| `objective-rrt/tools/` | Python: `viz.py` (tree server for the viewer), `export_tree.py`, `stars.py`, TAS analysis |
| `objective-rrt/ref/` | Research: TAS analysis and technique catalogue (`ref/tas/`), BLJ research (`ref/blj-conditions.md`), speed analysis (`ref/speed/`), saved wiki pages (`ref/INDEX.md`) |
| `objective-rrt/RUNS.md` | Every experiment: switches, results and lessons |
| `objective-rrt/builds/` | Build dirs and frozen experiment binaries (`snap-vNN/obrrt`); git-ignored |
| `objective-rrt/runs/`, `logs/` | Run outputs and logs; git-ignored |

## 1. Build

Run all commands below from `objective-rrt/`.

```sh
cargo build --release                         # -> target/release/obrrt
# or a separate build dir (copy an existing one so only our crates rebuild):
cp -a builds/target-v42 builds/target-mine
CARGO_TARGET_DIR=builds/target-mine cargo build --release
```

A global rustc gate (`/workspaces/sm64-combined/.cargo/rustc-gate.sh`, configured in `/workspaces/sm64-combined/.cargo/config.toml`) allows at most 4 rustc at once machine-wide (`RUSTC_GATE_SLOTS`), so parallel builds queue instead of running out of memory. The latest frozen binary is `builds/snap-v47/obrrt`.

## 2. Run the tree search

```sh
obrrt <rom> [out_dir=runs/obrrt] [seed=1] [minutes=30] [<start.m64>]
```

The current best configuration ("v46-mw"), 500 M emulated frames:

```sh
env OBRRT_SOFT_DEDUP=1 OBRRT_MEM_MB=3000 OBRRT_ROUND=64 OBRRT_MAX_FRAMES=500000000 \
    OBRRT_TECH=all OBRRT_NEW_ELIGIBLE=1 OBRRT_STARSET_KEY=1 OBRRT_PICK_BY_B=0 \
    OBRRT_SWIM_HOLD=1 OBRRT_GP_CATCH=1 OBRRT_KEEP_WIP=1 \
    OBRRT_MOVE_WEIGHT=0.75 OBRRT_TAS_BOOT=1 \
  ./builds/snap-v47/obrrt ../baserom.us.z64 runs/my-run 1 180 > logs/my-run.log 2>&1
```

- **Reproducible:** the same binary, seed and thread count (`RAYON_NUM_THREADS`; all cores by default) give byte-identical trees.
- **Budget:** `minutes` is a wall-clock cap. Set `OBRRT_MAX_FRAMES` below it so frames, not time, end the run.
- **Boot from a movie:** `<start.m64>` boots from a movie prefix instead of power-on. Add `OBRRT_BOOT_NOWAIT=1` to start where the prefix ends even if Mario is moving.
- **Resume:** `OBRRT_RESUME=runs/my-run` continues an existing tree.
- **Memory:** about 250 MB per 2 threads, plus the state store (`OBRRT_MEM_MB`). Full 16-thread runs use a few GB.
- **Time:** all frame counts are frames since power-on (`St.frame`, the same as the game's `gGlobalTimer`), at 30 per second.

Outputs in `runs/my-run/`:
- `nodes.csv`: one row per state (frame, position, level/area, stars, the objective that made it, ...);
- `events.jsonl`: every attempt;
- `summary.json`;
- `tree.bin`: inputs, used for resume and replays;
- `first-*.m64` and `frontier-*.m64`: replays from power-on.

The log prints progress every 30 s, plus "best times" (per star count) and "first arrivals" (per level and area).

## 3. Switches

Every behaviour change has a switch, and defaults keep the old behaviour.
- **`objectives/OBJECTIVES.md`:** every objective kind and every `OBRRT_*` switch, with its default.
- **`OBRRT_TECH`:** `all` / `none` / comma list / `-name` / tag (`movement`, `location`, `star`). Picks the speedrun techniques (registry in `objectives/src/extra/tech/mod.rs`).
- **`RUNS.md`:** which switches each experiment used, and what they did.

## 4. Look at results

- **Stars:** `python3 tools/stars.py <run>`. Run it on a few runs at a time, not all of `runs/`.
- **Viewer, live tree:**
  ```sh
  python3 tools/viz.py 8090 &                                  # tree server
  (cd ../../sm64-viewer/frontend && npx vite --host 0.0.0.0 --port 5173)
  ```
  Open `http://localhost:5173/sm64-viewer/?tree=<run>&zone=<level>:<area>&node=<id>`, or pick a run in the tree view. The viewer reads level geometry from your ROM in the browser. "Play in viewer" replays the path from power-on to the selected state.
- **Static export** (no tree server, e.g. GitHub Pages): `python3 tools/export_tree.py <run>` writes `../../sm64-viewer/frontend/public/trees/<run>/`. Add `?static=1` to the URL to force static mode.
- **Replay tools** (in any target dir's `release/`):
  - `nodepath <run> <node>`: an m64 from power-on to a node;
  - `tasplay`: play an m64 and dump per-frame state;
  - `probe`: inspect a frame;
  - `steertest`, `modalbench`;
  - `cargo run --release --example core_fields`: per-frame floor, ceiling and wall fields.
- **Speed:** `ref/speed/TIMELOSS.md` compares milestone frames (castle door, level entries, stars) with the 2026 120-star TAS in `ref/tas/`, and lists where time is lost.

## 5. Mupen64 savestates

`../sm64-binds` loads Mupen64-rr(-lua) and Mupen64Plus `.st` files into the port: `MupenState::from_file`, `load_mupen_state`, `warp_to_mupen_area`, and the check tool `cargo run --release --example mupen_check`. Formats and limits are in `../sm64-binds/docs/mupen64-st.md`.

## Rules the code follows

- SM64 knowledge lives only in `objectives/` (and `search/src/steer.rs`). The engine is generic. Heuristics use straight-line distance.
- No MCTS or UCB over states: RRT-style selection.
- Technique objectives must require the trick in their progress and success, never credit plain walking. Location techniques get only a rough start region and an endpoint; the general technique code does the rest.
